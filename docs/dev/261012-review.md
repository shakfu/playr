# Review: playr-gui feature set

2026-10-12, on `dev` at `c4d3845`, clean tree. Read-only: no code changed.

Scope: whether the window's features are essential and orthogonal, and whether they form a coherent whole. The sources are the README, `docs/dev/gui.md`, `docs/dev/mixer.md`, `docs/guide-dj.md`, `docs/guide-tape.md`, `TODO.md` and `docs/dev/261011-review.md`. Code was checked only where noted.

Evidence labels:

- **verified**: traced in the code.

- **documented**: stated in the docs named, not traced.

- **inference**: not traced.

## Summary

The window works as a workstation for mining tracks, but less well as the music player the README introduces. Its features connect through one workflow. They share few primitives, so one concept exists two or three times, with different ranges and APIs.

## What makes it coherent

The views share one workflow: **track -> mark -> range -> slice / loop -> instrument** (documented).

- Marks feed `:slice`, appear on the DJ overviews, and bound ranges.

- A range feeds the tape (`:tape load`) and the loop library. The loop library feeds the tape lanes.

- `playr analyze` feeds search (`tempo:`), ReplayGain and the DJ beat grids.

- Take hands the playing track to a deck or the tape.

- The mixer sums the player, tape and decks under one master.

Every view reads one `library.db`, and every control goes through `dispatch` (`docs/dev/261011-review.md`, "Architecture notes").

## Overlapping concepts

Each instrument reimplements a concept instead of sharing it (documented):

| concept | player | sampler | tape | DJ |
|-|-|-|-|-|
| EQ | 3-band, +/-12 dB | -- | HP/LP/bell per voice | isolator -24..+6 dB, kills, filter knob |
| rate | semitones/cents, 0.5-2x | -- | frames/frame, -4..4 | percent, ranges 8/16/50 |
| points in a track | marks | marks, range ends | windows | cue, 4 hot cues, marks (read-only) |
| loops | range `l` | range, slots F1-F8 | loop library | beat loops 0.25-32 |
| record | -- | slice export | `:tape save`, `rec`, `bounce` | via `:mix rec` |

Costs already paid:

- Take translates between these models. It drops the player's EQ, "whose curves differ" (`docs/guide-dj.md`). It maps semitones to "the rate fader in the narrowest range that holds it".

- Hot cues and marks are two persisted point types per track.

- The selection and the queue overlap. `TODO.md` lists their merge ("One list for the selection and the queue").

- The delay has 3 models and the reverb 4 (`TODO.md`, "Choose the effects' models"). This is a pending choice, not part of the feature set.

## Stated principle vs. the code

`docs/dev/gui.md` says the window "adds no features of its own". That no longer holds (verified):

- Tape, DJ and Mix are window-only views; `View::TERMINAL` excludes them (`crates/playr-app/src/lib.rs:69`).

- The sampler overview and Scrub are window-only (README, "Interfaces").

The window is now the superset, and the terminal is a command console for three of its views. Either `gui.md` should say so, or the parity goal should be dropped explicitly.

## Doc contradiction

The README's `:dj a play` row said it played the deck "pausing the player". Since 2026-10-06 a deck's start leaves the player playing (`docs/dev/mixer.md`, "Built"). `D::Play` sends only `Setting::Play` (`crates/playr-app/src/dj.rs:1074`, verified); only Take pauses the player (`hand_over`, `dj.rs:932`). `docs/guide-dj.md` was right. The README row is fixed.

## Concurrency

The tape's Play and both Takes pause the player. A deck's Play does not (`docs/dev/mixer.md`, "Built"). Nothing links the tape and the decks (`docs/dev/mixer.md`, "What exists", itself marked inference). That gives three sources with two concurrency rules.

## Alternative framings

1. **The player is a deck.** The DJ engine already plays tracks with rate, EQ, cues and loops. Merging removes Take, one EQ, one rate model and one transport. Cost: gapless playback, ReplayGain and the device-rate path in `playr-core` move into the deck. The deck reads the whole track into memory, which suits a deck but not a player.

2. **Shared primitives, separate instruments.** Keep the four engines. Define one point type, one loop type, one EQ description and one rate type in `playr-app`, which the instruments consume. This removes most of the overlap table without merging engines.

3. **Split the product.** One app holds the player, library and sampler. The other holds the tape and DJ. `library.db` and the loop library link them. This suits the 800-point width better than 8 tabs.

## Open questions

- Does anyone use DJ and tape in one session? If not, framing 3 costs little.

- Is the player a separate source by design, for listening while preparing decks, or only by history? This decides framing 1.

- Should the tape's Play pause the player when a deck's Play does not?

- Could hot cues and marks be one table with a kind column?
